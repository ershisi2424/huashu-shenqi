# 审批待办、已登录只读工作台、维护任务与游客临时工作台设计

## 背景与问题

当前应用出现四类相互关联的问题：

1. 最高管理员审批中心偶尔看不到待审批运营申请。
2. 运营或最高管理员从后台进入主播只读工作台时，可能被错误地跳回登录页。
3. 维护任务只能由系统根据确认消息自动创建，缺少人工新增入口。
4. 需要一个不要求密码的临时游客工作台，但不能让手机号成为访问正式主播私密数据的凭证。

排查确认：Service Worker 当前对同源 API 使用 URL 级 cache-first，缓存键不区分登录 Cookie；审批页面还把运营审批和主播审批放在一个 `Promise.all` 中。正式认证、只读范围和维护任务数据库模型已经存在，可以在其上扩展。游客当前只有本地 guest scope，没有服务端会话。

## 目标与非目标

### 目标

- 认证、审批、聊天、工作台快照和任务接口不再被跨账号缓存复用。
- 运营申请队列和主播申请队列独立加载、独立显示错误。
- 已登录运营/最高管理员进入授权主播工作台时复用当前会话，不需要二次登录；未登录和越权请求仍被拒绝。
- 主播、所属运营和最高管理员按角色范围创建人工维护任务，并写入审计。
- 游客使用手机号创建独立临时会话，可使用完整 GLM-5.3 候选回复，但只能操作自己的临时工作区。
- 游客退出后立即撤销会话；最后活动超过 24 小时且没有活动会话时，清理游客身份、会话和临时工作区数据。

### 非目标

- 不读取抖音后台私信、作品、评论或登录凭据。
- 不让游客查看任何主播、运营或最高管理员的正式聊天记录。
- 不自动向抖音发送消息；AI 结果仍由使用者选择、修改、复制并确认。
- 不改变运营审批主播、最高管理员审批全部申请的既有权限模型。

## 方案与架构

### 1. API 缓存与审批队列

Service Worker 对所有 `/api/` 请求直接放行到网络，不写入 runtime cache；激活新版本时删除旧 runtime cache。认证、审批、聊天、工作台快照和任务请求同时设置 `cache: "no-store"`，服务端私有 API 返回 `Cache-Control: private, no-store`，避免浏览器或反向代理缓存跨用户数据。

`ApprovalCenter` 对运营审批和主播审批分别发起加载并分别保存状态。最高管理员始终显示运营申请结果；主播审批接口失败时只显示主播队列错误。运营仍只请求并处理自己名下主播申请，不显示运营注册申请。

### 2. 已登录只读主播工作台

后台链接继续携带目标 `anchorId`，但不携带账号凭据。只读页先等待 `/api/auth/me` 返回当前用户，再请求工作台快照；请求使用当前同源 `hh_session`。服务端 `listReadonlyWorkspace` 继续执行角色范围检查：运营只能访问自己绑定的主播，最高管理员可访问全部主播。未登录返回 401，主播或跨运营访问返回 403。

失效会话显示“当前登录已失效”，提供回到登录页的入口；不把授权失败改成匿名访问，也不通过前端参数绕过服务端校验。

### 3. 人工维护任务

新增 `POST /api/chat/tasks/` 和 `createMaintenanceTask` 存储方法。请求字段：`brotherId`、`type`、`priority`、`title`、`reason`、`nextAction`、`dueAt`。人工任务的 `sourceMessageId` 为空，不伪造来源消息；状态初始为 `follow_up`，以区别系统自动生成的 `reply/pending_reply` 任务。

权限规则：

- 主播只能为自己拥有的维护对象创建任务。
- 运营只能为自己管理范围内主播的维护对象创建任务。
- 最高管理员可为全部主播对象创建任务。
- 任务创建动作写入 `chat.task.create` 审计，记录对象、任务类型和创建角色。
- 现有主播状态更新、已发送自动完成和运营/最高管理只读规则保持不变。

任务中心和聊天页增加简洁的“新增维护任务”表单；提交后刷新当前对象任务卡，并允许勾选是否将该任务建议带入下一轮 AI 生成。

### 4. 游客临时工作台

游客使用独立的 `guest_accounts` 与 `guest_sessions` 数据模型，不扩展正式用户角色，也不复用正式用户密码登录：

- `guest_accounts` 保存随机 guest id、手机号 HMAC（不保存明文手机号）、创建时间、最后活动时间、退出时间和过期时间。
- `guest_sessions` 保存 token hash、guest id、创建时间、最后活动时间、过期时间和撤销时间。
- Cookie 使用 `hh_guest_session`，与 `hh_session` 分离。
- `/api/auth/guest-login` 接收手机号，创建新的临时游客身份和会话；手机号不恢复或访问正式账号数据。
- `/api/auth/guest-me` 返回游客状态、匿名显示名和剩余有效期；每次游客业务请求更新最后活动时间。
- `/api/auth/logout` 同时支持撤销正式会话或游客会话；游客退出时立即标记撤销。

游客工作台使用现有聊天交互外观，但数据仅保存在游客命名空间的临时工作区；游客可以输入大哥消息、生成完整 AI 候选、选择后修改并复制回复。游客请求不进入正式审批、运营复盘、正式审计或主播只读工作台。

清理策略在游客登录、游客业务请求、游客登出和服务启动时执行：删除没有活动会话且 `last_seen_at` 超过 24 小时的 guest account、guest session 和游客临时数据。清理使用事务和明确的 guest id 条件，不能删除正式用户或正式聊天数据。

### 5. AI 与安全边界

游客 AI 请求只允许使用游客当前输入、游客临时历史和公开/授权文本；不能携带正式主播的 `brotherId`、消息 ID、长期记忆或工作台快照。AI 仍使用现有 goutoujunshi Runtime 与 GLM-5.3 输出校验，不改变“不推断敏感属性、不诱导消费、不自动发送”的边界。

## 错误处理

- API 缓存命中被禁止后，旧 Service Worker 通过版本升级和 activate 清理；页面遇到 401/403 时区分“会话失效”和“无权访问”。
- 审批两个队列分别显示加载、空状态和错误；一个接口失败不清空另一个队列。
- 任务 POST 对缺少对象、越权对象、非法状态/优先级和空标题返回明确 400/403/404。
- 游客会话失效返回 401，并清除游客 Cookie；游客只能看到自己的临时工作区。
- 清理失败只记录脱敏错误，不影响当前请求，也不影响正式账号。

## 验收与测试

### 自动化契约

- Service Worker：`/api/` 不进入 cache-first，版本升级清除旧 runtime cache。
- 审批 API/UI：运营待办在主播审批接口失败时仍可渲染；最高管理员能看到 pending operator；运营看不到运营注册队列。
- 会话隔离：账号 A 登出后账号 B 获取到 B 的 `/api/auth/me`、聊天和审批数据；缓存不会返回 A 的数据。
- 只读工作台：带有效运营/最高管理员会话返回 200；无会话返回 401；跨运营或主播身份返回 403。
- 维护任务：三种角色按范围创建，其他对象拒绝；任务来源为空并写入审计；旧自动回复任务流程不回归。
- 游客：手机号登录得到独立会话；游客可生成候选但不能访问正式对象；退出撤销会话；模拟 24 小时无活动后清理游客数据；正式账号和聊天记录保留。

### 浏览器复核

- 先登录主播 A，再退出并登录最高管理员，刷新审批和聊天页面，确认身份、待办和数据不串号。
- 最高管理员从后台进入主播只读工作台不再跳登录；直接匿名打开仍被拦截。
- 运营和最高管理员从任务中心新增任务，主播看到任务并可按现有规则更新。
- 游客手机号登录后进入空白临时工作台，生成 AI 候选，退出后重新访问不可恢复旧游客内容，清理后正式账号数据不变。

## 迁移与兼容

- 旧正式用户、聊天消息、任务和快照不迁移、不删除。
- Service Worker 只清理旧缓存，不修改 SQLite 正式数据。
- 游客表和临时工作区表使用 `IF NOT EXISTS`，启动时可安全重复执行迁移。
- 旧客户端在服务端收到失效缓存后会通过 401/刷新回到当前会话；不会获得更宽的权限。
