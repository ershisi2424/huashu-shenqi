# 全量审计查看页设计

日期：2026-09-30  
状态：已确认范围，待实现

## 背景与目标

当前服务已经将登录、审批、账号创建、聊天对象创建和消息确认等关键动作写入 SQLite 的 `audit_logs`。运营后台目前只能看账号统计和最近消息，缺少按操作时间线复盘的能力。本阶段新增只读审计查看页，让运营和最高管理按照组织层级查看下一级的全部操作，并在聊天操作上展开实际消息正文。

## 已确认的权限范围

- 最高管理（`super_admin`）：查看全部运营、全部主播和系统产生的审计记录。
- 运营（`operator`）：查看自己的操作，以及自己所辖主播的全部操作；包含主播申请、登录、维护对象、消息确认和发送标记等记录。
- 主播（`anchor`）：不能进入运营审计页，也不能调用审计接口。
- “下一级”只表示组织层级的下属操作，不代表运营可以查看其他运营或其他运营名下主播的数据。
- 聊天正文只在调用者已有权限的审计记录中展示。审计日志不复制正文，页面读取时关联 `chat_messages`。

## 非目标

- 不连接抖音私信或自动发送消息。
- 不允许审计页编辑、删除、重放或代替主播发送聊天内容。
- 不在审计响应中返回密码哈希、会话令牌、完整密钥或未授权账号的手机号。
- 不改变现有服务端聊天消息的所有权和运营只读复盘规则。

## 数据与接口设计

### 服务端查询

扩展 `lib/auth-store.cjs` 的审计查询为带调用者的分页查询：

```text
listAuditLogs({ actor, limit, cursor, action, role, from, to })
  -> { items, nextCursor }
```

查询在服务端完成权限过滤和关联：

- 最高管理不加组织过滤。
- 运营通过 `actor_user_id`、操作者的 `users.operator_id` 或目标主播的 `users.operator_id` 限定到自己和自己的主播。
- 排序固定为 `created_at DESC, id DESC`；游标包含最后一条的时间和 ID，避免同一时间戳造成重复或漏项。
- `action`、`role`、时间范围均使用参数化条件；`limit` 限制在 1–100。
- 关联操作者和目标账号时只返回展示所需的 ID、名称、角色和脱敏手机号。

新增 `GET /api/ops/audit/`，仅允许 `operator` 与 `super_admin`。返回结构：

```json
{
  "items": [{
    "id": "...",
    "action": "chat.message.append",
    "actor": { "id": "...", "name": "主播一号", "role": "anchor", "phone": "137****00" },
    "target": null,
    "metadata": { "sender": "brother", "status": "confirmed" },
    "createdAt": "2026-09-30T00:00:00.000Z",
    "chatMessage": {
      "id": "...",
      "brotherNickname": "山哥",
      "sender": "brother",
      "direction": "left",
      "status": "confirmed",
      "text": "晚上好",
      "confirmedAt": "...",
      "sentAt": null
    }
  }],
  "nextCursor": "..."
}
```

`chatMessage` 只对 `metadata.messageId` 能关联到且调用者有权限的消息返回；消息已不存在时返回 `null`，审计记录仍保留。关联消息正文使用现有清洗后的 `chat_messages.text`，不从客户端重新接收正文。

### 审计数据安全

服务端解析元数据时对敏感键做递归清洗（`password`、`token`、`secret`、`key`、`cookie` 等），即使历史数据误写也不会直接回传。前端使用 React 文本渲染，不使用 `dangerouslySetInnerHTML`。接口错误只返回通用权限/查询失败信息。

## 后台页面设计

在现有 `/admin` 页面增加“操作审计”区域：

- 顶部显示当前账号和权限范围。
- 提供角色、动作和时间范围筛选；默认加载最近 50 条。
- 每条记录显示时间、操作者、角色、动作、目标、维护对象和状态元数据。
- 具备聊天正文的记录显示“展开聊天正文”控件；展开后区分“大哥（左侧）/主播（右侧）”、显示正文和确认/发送状态。
- 提供“加载更多”，使用服务端游标，不使用无限制一次性加载。
- 无数据、加载、错误和无权限状态保持与现有后台视觉规范一致，并适配手机宽度。
- 审计区为只读，页面不出现编辑、删除、重新发送按钮。

## 错误与边界

- 未登录返回 401，主播或其他角色返回 403。
- 游标、时间和筛选参数非法时返回 400，不回退到全量查询。
- 关联消息不存在时显示“正文已不可用”，不阻塞其他审计记录。
- SQLite 查询异常记录服务端错误日志，但响应不包含数据库路径或敏感参数。

## 测试与验收

1. 存储层：最高管理得到全量；运营得到自己的操作和所辖主播操作；另一个运营及其主播不可见；主播调用被拒绝。
2. 存储层：`chat.message.append` 能关联大哥/主播方向、正文和发送状态；缺失消息返回 `null`。
3. API：验证 401/403、筛选、分页游标、角色隔离和敏感字段清洗。
4. UI：验证审计区域、筛选控件、展开正文、加载更多、空态和移动端文案存在。
5. 回归：`npm test`、`npm run build`、`git diff --check`，并对运行中的 `3102` 服务做登录后 HTTP 验证。

## 验收标准

- 最高管理登录 `/admin` 后可以查看所有运营及主播的操作和聊天正文。
- 运营登录后只能查看自己及所辖主播的全部操作和正文，无法通过修改查询参数越权。
- 主播无法打开审计接口。
- 审计正文与现有聊天记录一致，且不会自动改变已发送状态。
- 既有登录、审批、聊天同步和运营复盘测试保持通过。
